Customer Support Ticket API (Mobile)
Customer → Owner support tickets, as JSON, for the mobile apps.
This is the API mirror of the storefront flow at /account/support-ticket. A ticket
raised here lands in the owner's inbox at /owner/support-tickets/:id, and the owner's
reply comes back down the same thread.
Controller: src/controllers/api/CustomerSupportTicketController.ts
Base path: /api/customer/support-tickets
Content types: multipart/form-data for anything with an attachment
  (POST /, PUT|PATCH /:id, POST /:id/replies), application/json accepted
  for those same routes when you are NOT sending a file.

Not the same as /api/v1/support-tickets**.** That older controller still exists
(create + replies only) and is left untouched for backwards compatibility. New mobile
work should use the routes in this document — they are fully ownership-scoped, the
/api/v1 ones are not. See Appendix B. 



1. Headers
There are two independent credentials on every request — the store's API key and the
customer's session token. Both must be present or the request is rejected.
HeaderValueRequiredWhyaccess-key





the website's 48-character API key





yes





Identifies and authorises the store. Validated against the ApiKey collection for the resolved website.





Authorization





Bearer





yes





Identifies the customer. Cookies also work, but mobile should use the bearer header.





Accept





application/json





yes





The API-key check rejects the request outright if Accept is not exactly application/json.





Host





the store's domain, e.g. mystore.com





yes





The website is resolved from the Host header, and the access-key is then validated against that website.








Plain Text








POST /api/customer/support-tickets HTTP/1.1
Host: mystore.com
access-key: 0f3c9a1b7e2d4c8a6b5f0e9d3c7a1b4e8f2d6c0a9b3e7f1d
Authorization: 
Accept: application/json
Content-Type: multipart/form-data


The two credentials do different jobs
access-key → the store. Enforced globally by apiKeyCheckContext
  (src/middleware/global/apiKeyCheckContext.ts, priority 6) for every /api/\\* route not on
  its exclusion list. It checks three things: Accept is exactly application/json, the key
  is exactly 48 characters, and the key exists in the ApiKey document for the website**resolved from the Host header**. Results are cached for 60s. A key from store A sent to
  store B's domain fails.
Authorization: Bearer → the customer. Checked afterwards by the controller's
  requireCustomer guard. Get the token from POST /api/auth/login (see
  src/controllers/api/AuthController.ts) — the same customer token used for orders, cart and
  addresses works here, no separate login.

Note: the older /api/v1/support-tickets routes are explicitly excluded from the
API-key check (they are named in the middleware's skip list). These /api/customer/...
routes are not excluded, so unlike the old ones they do require access-key. This is
deliberate — it is one of the reasons to prefer these routes. 
⚠️ All 9 routes require an authenticated customer. There is no guest access. Unlike the
storefront, there is no "raise a ticket without an account" path.
API-key failure
A missing, malformed, wrong-length, or wrong-store key — or a missing/incorrect Accept
header — fails before the controller runs, with a third response shape (see
§5):


Plain Text








HTTP/1.1 403 Forbidden




JSON








{
  "status": "error",
  "data": "You do not have permission to perform this action."
}


The message is deliberately generic and identical for all of those causes, so it will not tell
you which header was wrong. When debugging a 403, check in this order: Accept is exactly
application/json → key is 48 chars → key belongs to the store in Host.

5. Error format
⚠️ There are three different error shapes, depending on which layer rejected the request.
This is the single most common integration trap on this API — a client that only reads
message will show blank alerts for two of the three.
Shape 1 — API-key layer (access-key / Accept)
Rejected first, before anything else runs.


JSON








{
  "status": "error",
  "data": "You do not have permission to perform this action."
}


Shape 2 — auth layer (Authorization)


JSON








{ "error": "Unauthorized" }


Shape 3 — the controller (everything documented in §4)


JSON








{ "success": false, "message": "Support ticket not found" }


Reading them


Plain Text








const msg = body.message ?? body.error ?? body.data ?? "Something went wrong";


Which code means what
CodeShapeBodyWhen403





1





{"status":"error","data":"You do not have permission…"}





Bad/missing access-key, wrong length, key not valid for this store, or Accept is not application/json.





401





2





{"error":"Unauthorized"}





Missing / expired / invalid customer bearer token.





403





2





{"error":"Forbidden"}





Valid token, but not a customer (e.g. an owner token).





400





3





{"success":false,"message":…}





Validation / bad state / missing website context.





404





3





{"success":false,"message":"Support ticket not found"}





Not found, or not yours.





500





3





{"success":false,"message":…}





Server error.






Both 403s look alike but mean opposite things. Shape 1 (status/data) is the store's__key is wrong — a build/config problem, retrying won't help. Shape 2 (error) is the user__is not a customer. Distinguish them by which key the body carries, not by the status code. 
Treat a 401 as "send the user to login". Treat a 403 with data as "the app's API key
is misconfigured" — do not log the user out for it.

6. Typical app flow


Plain Text








POST /api/auth/login                     → token
GET  /api/customer/support-tickets/meta  → dropdown values (cache it)
Support list screen
  GET  /api/customer/support-tickets?page=1
"Raise a ticket"
  POST /api/customer/support-tickets     → 201, ticket.id
Ticket detail screen
  GET  /api/customer/support-tickets/{id}          → ticket + thread
  POST /api/customer/support-tickets/{id}/replies  → 201
  (refresh thread, or append the returned reply locally)
Resolved
  POST /api/customer/support-tickets/{id}/close


Notes for the client
Set access-key and Accept: application/json once in the shared HTTP client, next to
  wherever the bearer token is injected. They are required on every call here, and a
  missing one surfaces as a confusing generic 403.
There are no push/websocket events on this module. Owner replies arrive by
  WhatsApp/Telegram/email; in-app you must poll GET /:id or pull-to-refresh.
Only one attachment per ticket and per reply.
Poll the list screen, not the detail screen, to badge unread — updated_at moves when the
  owner replies.




Appendix A — cURL


Bash








BASE="https://mystore.com"
TOKEN="eyJhbGciOi..."                                              # customer bearer token
KEY="0f3c9a1b7e2d4c8a6b5f0e9d3c7a1b4e8f2d6c0a9b3e7f1d"            # 48-char store API key
# Every call needs all three: access-key, Authorization, Accept.
AUTH=(-H "access-key: $KEY" -H "Authorization: Bearer $TOKEN" -H "Accept: application/json")
# List
curl -s "${AUTH[@]}" "$BASE/api/customer/support-tickets?page=1&limit=10"
# Meta
curl -s "${AUTH[@]}" "$BASE/api/customer/support-tickets/meta"
# Create with attachment
curl -s -X POST "${AUTH[@]}" "$BASE/api/customer/support-tickets" \
  -F "subject=Order not delivered" \
  -F "message=Order #1042 has not arrived." \
  -F "priority=high" \
  -F "image=@/path/to/receipt.jpg"
# Create without attachment (JSON)
curl -s -X POST "${AUTH[@]}" "$BASE/api/customer/support-tickets" \
  -H "Content-Type: application/json" \
  -d '{"subject":"Order not delivered","message":"Order #1042 has not arrived.","priority":"high"}'
# Detail
curl -s "${AUTH[@]}" "$BASE/api/customer/support-tickets/66f1a2b3c4d5e6f7a8b9c0d1"
# Edit
curl -s -X PATCH "${AUTH[@]}" "$BASE/api/customer/support-tickets/66f1a2b3c4d5e6f7a8b9c0d1" \
  -H "Content-Type: application/json" \
  -d '{"priority":"high"}'
# Replies
curl -s "${AUTH[@]}" "$BASE/api/customer/support-tickets/66f1a2b3c4d5e6f7a8b9c0d1/replies?page=1"
# Reply
curl -s -X POST "${AUTH[@]}" "$BASE/api/customer/support-tickets/66f1a2b3c4d5e6f7a8b9c0d1/replies" \
  -F "message=Still not received."
# Close
curl -s -X POST "${AUTH[@]}" "$BASE/api/customer/support-tickets/66f1a2b3c4d5e6f7a8b9c0d1/close"


If any of these return {"status":"error","data":"You do not have permission…"}, the
access-key/Accept pair is the problem, not the token.
